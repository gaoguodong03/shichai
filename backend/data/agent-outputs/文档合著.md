# 技术决策说明书 (ADR)：单体服务向微服务架构演进（第一阶段）

| 状态 | 提议中 | 负责人 | [您的名字/团队名] |
| :--- | :--- | :--- | :--- |
| **日期** | 2023-10-27 | **评审人** | 技术委员会、产品部负责人 |

## 1. 背景 (Context)
当前“黑盒单体”系统已进入瓶颈期，主要表现为：
*   **开发效率受阻**：8人团队在单一代码库协作，编译部署慢，新人上手成本极高。
*   **资源抢占严重**：高并发的“订单履约”模块频繁触发 OOM，影响全站稳定性。
*   **数据库风险**：核心表 `order_related` 已逼近 5000 万行预警线，单库单表扩展性见顶。
*   **业务诉求**：产品部要求提升交付频率，技术委员会要求实现独立扩缩容与清晰的业务边界。

## 2. 决策 (Decision)
我们决定采用**“服务逻辑剥离，数据库物理耦合”**的渐进式拆分策略（方案 A）。

### 2.1 核心动作
1.  **服务拆分**：将单体工程拆分为 `Order-Service`（订单）、`Fulfillment-Service`（履约）和 `Inventory-Service`（库存）三个独立微服务。
2.  **技术栈对齐**：统一使用 Java + Spring Boot，复用现有 K8s + GitLab CI + Kong 网关。
3.  **数据访问**：三个服务在第一阶段**共用**现有的 `order_related` 物理数据库，但通过代码规范和 DAO 层限制，确保各服务仅访问其所属业务域的表。
4.  **基础设施补齐**：在不引入 Service Mesh 的前提下，优先集成全链路追踪（如 SkyWalking 或 Zipkin），以应对分布式调用下的排障需求。

## 3. 方案细节与理由 (Rationale)

### 3.1 为什么选择“逻辑拆分，物理共库”？
*   **降低首期复杂度**：避免同时进行“服务拆分”与“物理拆库+分布式事务改造”带来的双重风险。
*   **理清调用边界**：通过接口（REST/RPC）代替进程内调用，强制梳理订单与库存间的强事务依赖，为后续物理拆库打样。
*   **平滑过渡**：5000 万行数据虽有压力，但仍有数月的缓冲期。我们利用这段窗口期先让服务跑稳，再规划第二阶段的数据迁移。

### 3.2 团队组织架构调整
*   8人团队将按业务域划分为 3 个小组，实现“谁开发，谁运行，谁负责”，解决部署冲突问题。

## 4. 影响与风险评估 (Consequences)

### 4.1 正向影响 (Pros)
*   **独立部署**：订单履约模块可根据流量独立扩容，不再受单体资源限制。
*   **交付加速**：代码库解耦后，各小组可并行开发、测试与发布，提升产品迭代效率。
*   **架构演进**：建立了清晰的微服务治理规范（CI/CD、链路追踪），为后续全面微服务化打下基础。

### 4.2 负面影响与风险 (Cons & Risks)
*   **数据库单点风险**：物理上仍是单库，若数据库发生宕机，所有服务依然受累。
*   **分布式排障成本**：跨服务调用增加了网络开销和排障难度（需通过链路追踪缓解）。
*   **“伪拆分”诱惑**：由于物理共库，开发者可能绕过接口直接跨库查询。**对策**：通过代码扫描和数据库权限控制严格限制跨域访问。

## 5. 后续规划 (Next Steps)
1.  **第一阶段（当前）**：完成逻辑拆分，实现服务独立部署。
2.  **第二阶段（预估 3-6 个月后）**：待接口稳定且数据量接近极限时，启动库存库物理拆分，引入 TCC 或 Saga 模式处理分布式事务。
