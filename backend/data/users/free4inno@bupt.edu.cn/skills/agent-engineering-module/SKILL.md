# Agent 工程与框架实践模块 Skill

## 模块定位

适用于以下场景：

1. 设计一个新的 Agent / 多 Agent 协同系统  
   - 例如：研究助手、代码助手、知识库问答、工作流自动化等
2. 为现有系统增加 MCP 工具或 Skill，或重构 Skill 结构  
3. 需要在 LangChain / 其他 Agent 框架中选择合适的模式（Tool-Calling、Router、Plan & Execute 等）
4. 对现有 Agent 系统做工程级评审（可维护性、可扩展性、鲁棒性等）

## 基本概念视角

当使用本模块时，优先从以下几个视角思考：

- **任务分解视角**：用户需求 → 任务树 / 步骤流
- **Skill 模块视角**：哪些能力应该抽成独立 Skill / 模块（单一职责，可复用）
- **工具（Tool）视角**：哪些动作需要真正访问外部世界（HTTP、文件、数据库、浏览器、执行环境等）
- **框架模式视角**：当前要用的是：
  - 简单链式调用（Chains）
  - 单 Agent + 多 Tools
  - 多 Agent 协同（如 Router / Manager-Worker 等模式）

## 推荐推理流程（供“果冻”主体参考）

### 步骤 1：明确目标与环境

1. 用户/业务目标是什么？  
2. 当前运行环境与约束（本地 / 后端服务 / 有无数据库 / 有无浏览器 / 有无 MCP）？  
3. 是否需要长期记忆、会话上下文、多轮对话等能力？

### 步骤 2：任务分解与 Skill 拆分

1. 把目标拆成若干**子任务**（最好可以画成简单有向图）：  
   - 信息收集（搜索 / 抓取 / 读取文件）  
   - 分析与推理  
   - 生成内容或执行操作  
   - 结果检查与修正
2. 为每类子任务考虑是否需要独立 Skill：  
   - 通用型能力（如“计算机系统知识模块”“河南知识模块”“写作模块”）  
   - 专用型能力（如“某具体业务流程助手”）

### 步骤 3：工具与接口设计

1. 确定需要哪些外部工具（用 MCP 或其他方式实现）：  
   - Web / 搜索 / 抓取  
   - 文件读写 / 数据库访问  
   - 浏览器自动化 / 第三方 API
2. 为每个工具设计：  
   - **输入参数**：结构化、尽量与业务语义一致  
   - **输出结构**：包含机器可用的字段 + 摘要文本  
   - 清晰的错误与异常约定（例如网络失败、权限不足等）

### 步骤 4：选择框架模式（以 LangChain 为例）

结合任务结构与复杂度，选择合适模式：

- 简单线性流程：用 Chains 或顺序调用即可
- 工具丰富但单 Agent 即可胜任：用 Tool-Calling 型 Agent
- 不同领域能力较强且明显：  
  - 使用 Router / Multi-Agent 模式，根据用户问题路由到对应 Skill  
  - 或设计 Manager-Worker 结构（Manager 负责拆任务与聚合结果）

### 步骤 5：鲁棒性与可演进性

为每个设计方案，从工程角度检查：

1. **错误处理**：  
   - 工具失败时，Agent 应如何反馈与重试  
   - 是否需要降级路径（例如搜索失败时改用缓存知识）
2. **可观测性**：  
   - 是否便于日志记录、调试和统计（哪些步骤耗时、哪些工具常出错）  
3. **可演进性**：  
   - 后续新增一个 Skill / 工具时，是否只需改动少量路由逻辑  
   - 尽量避免把所有逻辑写死在同一个系统提示里
