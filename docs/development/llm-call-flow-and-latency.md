# LLM 调用流程与耗时分析

本文档说明每轮用户消息会触发多少次大模型调用，以及可优化点。

---

## 一、单聊 (Chat) 流程

### 1.1 调用链

```
用户发一条消息
  │
  ├─ ① select_skill()  — 1 次 LLM
  │     （若前端已传 skill_ids 且仅 1 个，则跳过）
  │
  ├─ 固定延迟 asyncio.sleep(QWEN_REQUEST_DELAY_SEC)  — 默认 1 秒
  │     （.env 中 QWEN_REQUEST_DELAY_SEC 默认 "1"，为防 DashScope 限流）
  │
  └─ ② 技能执行 ReAct 图
        agent 节点 → [若输出 tool_call] → tool 节点 → agent 节点 → … → end
        每次进入 agent 节点 = 1 次 LLM
```

### 1.2 单聊 LLM 次数（每条用户消息）

| 阶段           | 次数 | 说明 |
|----------------|------|------|
| 技能选择       | 0 或 1 | 前端传唯一 skill_id 时跳过 |
| 技能执行·首次  | 1 | 决定是否调工具或直接回复 |
| 技能执行·每次工具后 | 1 | 每执行完一批工具，再调一次 LLM 决定下一步 |
| **合计**       | **1 + (1 + 工具调用次数)** 或 **0 + (1 + 工具调用次数)** | 例如：读文件 + 写文件 = 2 次工具 → 至少 3 次 LLM（执行阶段） |

典型「读文件并写总结」：**1（选技能）+ 1（延迟）+ 3（执行：先读→再写→收尾）= 5 步**，其中 **LLM 调用 = 1 + 3 = 4 次**，另加 **1 秒固定延迟**。

---

## 二、群聊 (Group) 流程

### 2.1 调用链（每轮自动模式）

```
用户发一条消息（或继续）
  │
  ├─ ① 主持人 leader_decide()  — 1 次 LLM
  │     决定下一发言人 (next_speaker)
  │
  └─ ② 当前发言人 DHA 的 ReAct 图
        agent → [若 tool_call] → tool → agent → … → end
        同上，1 + 工具次数 次 LLM
```

### 2.2 群聊 LLM 次数（每轮）

| 阶段     | 次数 |
|----------|------|
| 主持人   | 1    |
| 发言人执行 | 1 + 工具调用次数 |
| **合计** | **2 + 工具调用次数** |

同一轮内「读文件 + 写总结」：**1（主持人）+ 3（发言人：读→写→收尾）= 4 次 LLM**。

---

## 三、为何感觉慢

1. **固定延迟 1 秒**：单聊在技能选择后默认 `sleep(1)`，每条消息至少多 1 秒。
2. **技能选择多一次 LLM**：未传 `skill_ids` 或传多个时，会先调一次 LLM 只做路由。
3. **ReAct 每步一调**：每执行一个工具就再调一次 LLM，工具多则调用次数线性增加。
4. **群聊多一个主持人**：每轮多 1 次主持人 LLM。

---

## 四、已做 / 建议的优化

| 优化项 | 说明 | 状态 |
|--------|------|------|
| 单技能时跳过 select_skill | 前端传 `skill_ids` 且长度为 1 时不再调 LLM 选技能 | ✅ 已有 |
| 仅一个可选技能时跳过 select_skill | 即使未传 `skill_ids`，若 `skills_for_selection` 仅 1 个也直接选用 | ✅ 已做 |
| 默认不延迟 | `QWEN_REQUEST_DELAY_SEC` 默认改为 0；需防限流时在 .env 设为 1 | ✅ 已做 |
| 主持人/选人逻辑合并或缓存 | 群聊主持人可考虑与首轮发言人合并或缓存，减少一次 LLM | 可选 |
