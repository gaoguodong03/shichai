# 协作场景主持人与专家提示词对齐设计

## 目标

将用户 `user-d8f26bf88991429789b4905ba0ae8040` 的协作场景资源对齐到当前提示词和 Skill 分层规则，同时保持资料检索、文档合著、图片生成三类业务能力及其确认门禁不变。

迁移完成后：

- 场景提示词只描述协作任务契约；
- 主持人长期提示词承载跨场景调度规则和主持人输出合同；
- 主持人 Skill 只保留具体场景的四列表；
- 专家长期提示词承载跨场景专业边界、执行原则和专家输出合同；
- 普通专家 Skill 只保留业务执行规则和自然结束条件。

## 提示词分层

### 场景共享提示词

`scenario.json.system_prompt` 从空值改为协同写作任务契约，包含：

- 适用范围：公开资料研究、结构化写作、配图与图文装配；
- 共同要求：后续角色只使用用户已确认且真实存在的材料和产物；
- 确认门禁：候选来源、写作大纲、章节内容、配图方案和生成图片分别按绑定 Skill 的规则确认；
- 完成标准：用户实际要求的资料、文档、图片或图文版已经形成并可交付；
- 非目标能力不强制执行，用户只要求其中一个环节时，完成该环节即可结束。

场景提示词不描述阶段跳转、专家长期职责、普通 Skill 步骤、平台 JSON 或通用工作区函数。

### 主持人长期提示词

`scenario.json.host.system_prompt` 使用前端 `DEFAULT_HOST_SYSTEM_PROMPT` 的完整职责形状，保留以下内容：

- 纯调度边界；
- 一次只调度一位专家；
- 自包含任务单要求；
- 读取真实工作区材料但不代替专家生产业务产物；
- 四列表读取规则；
- `current_phase`、`message`、`suggested_add_agent_names` 输出合同。

长期提示词保持跨场景通用，不写死协作场景阶段、三个专家名称或具体 Skill 业务步骤。

### 专家长期提示词

三个 `agent.json.system_prompt` 使用相同的完整结构，并注入各自专业差异：

1. `职责边界`：负责什么、明确排除什么、不选择下一位专家、不推进场景阶段；
2. `专业标准`：保留检索可追溯性、文档结构一致性或视觉一致性要求；
3. `执行要求`：服从主持人本轮任务单，使用当前 Skill，基于真实输入和工具结果执行，按需读写工作区；
4. `输出`：只输出 `execution_status`、`message`、`next_action` 构成的 JSON；
5. `流程控制`：根据当前 Skill 的自然业务事实映射 `continue/respond` 与 `keep/release`。

由于非空专家提示词会完全替代平台默认提示词，三个资源都必须保存完整合同，不能只保存专业补充段落。

## 主持人 Skill

`skill-0909791c1d74/SKILL.md` 的 Frontmatter 保持当前字段，正文改为标题加唯一四列表。拟定流程如下：

| 决策前阶段 | 判定条件 | 本轮动作 | 决策后阶段 |
| --- | --- | --- | --- |
| （无） | 用户尚未给出可执行目标或缺少决定首个专业环节所需的信息 | 询问用户：请说明需要交付的资料、文档、图片或图文版，以及已有材料 | （无） |
| （无） | 用户要求搜索、抓取 URL、核验来源，或写作任务明确要求先取得公开资料 | 调度`信息检索专家`：根据用户目标取得可追溯资料，保存实际素材，并以可供用户确认的来源和路径作为完成条件 | 资料检索 |
| （无） | 用户要求写作或修改文档，并且已有可用材料或不需要公开资料检索 | 调度`文档合著专家`：根据用户目标和已有材料推进文档，交付当前确认门禁要求的实际文件 | 文档合著 |
| （无） | 用户只要求图片、配图或图文装配，并且已有明确内容依据 | 调度`图片生成专家`：根据已确认内容和视觉要求推进配图，交付当前确认门禁要求的实际方案、图片或图文版 | 图片生成 |
| 资料检索 | 尚未形成满足用户目标的真实候选来源或素材文件，且继续执行不需要用户补充 | 调度`信息检索专家`：继续检索或抓取并补齐可追溯素材，以形成可供确认的实际文件为完成条件 | 资料检索 |
| 资料检索 | 候选来源或素材已经形成，但用户尚未确认采用范围或资料是否足够 | 询问用户：请确认采用哪些来源，或现有资料是否已经足够 | 资料检索 |
| 资料检索 | 用户已确认资料，且目标还包括文档写作 | 调度`文档合著专家`：使用用户已确认的真实资料推进文档，交付当前写作确认门禁要求的文件 | 文档合著 |
| 资料检索 | 资料检索已经完成，用户剩余目标包括图片或图文装配且不包括文档写作 | 调度`图片生成专家`：使用用户已确认的真实资料和视觉要求推进配图，交付实际方案、图片或图文版 | 图片生成 |
| 资料检索 | 用户已确认资料，目标只包括资料交付 | 告知用户协作结束：所需研究资料已经形成并确认 | end |
| 文档合著 | 大纲、当前章节或修订稿已经形成，但正在等待用户确认或反馈 | 询问用户：请确认当前文档成果，或说明需要修改的内容 | 文档合著 |
| 文档合著 | 用户已给出当前文档成果的确认或修改意见，且文档尚未满足完成标准 | 调度`文档合著专家`：依据用户最新确认或反馈继续文档工作，交付下一份需要确认的实际文件 | 文档合著 |
| 文档合著 | 最终文档已经形成并满足写作要求，且用户还要求配图或图文版 | 调度`图片生成专家`：以最终文档和用户视觉要求为依据推进配图，交付实际方案、图片或图文版 | 图片生成 |
| 文档合著 | 最终文档已经形成并满足要求，且用户不需要继续配图 | 告知用户协作结束：所需文档已经形成 | end |
| 图片生成 | 配图方案或生成图片已经形成，但正在等待用户确认方案、图片或是否装配 | 询问用户：请确认当前配图成果，或说明需要修改及是否装配 | 图片生成 |
| 图片生成 | 用户已确认或提出修改要求，且所需图片或图文版尚未满足完成标准 | 调度`图片生成专家`：依据用户最新确认或反馈继续生成或装配，交付可验证的图片或图文版 | 图片生成 |
| 图片生成 | 用户要求的图片已经确认完成，或图文版已经形成 | 告知用户协作结束：所需视觉产物已经形成 | end |

表格使用运行时首轮实际传入的 `（无）` 作为初始阶段，不要求修改运行时代码建立额外初始状态。

## 普通专家 Skill

三个业务 Skill 继续使用 `执行规则` 和 `结束条件` 两个正文部分。修改仅用于收敛边界和措辞：

- 保留资料检索的搜索、抓取、逐来源保存和可追溯要求；
- 保留文档合著的大纲确认、逐节确认、版本化和最终合并要求；
- 保留图片生成的做图大纲确认、真实生成结果确认和图文版另存要求；
- 等待、完成和失败只写自然业务事实；
- 不写专家身份、主持人阶段、JSON 字段、工作区通用函数或技术流程控制枚举。

## 验证设计

先修改 `backend/tests/test_collaboration_scenario_resources.py`，使旧资源在新契约下失败，再修改资源使其通过。测试至少覆盖：

1. 场景提示词非空，包含共同目标和完成标准，不包含阶段表或平台 JSON；
2. 主持人长期提示词包含纯调度边界、四列表规则和当前输出字段，不写死具体专家；
3. 主持人 Skill 正文只有一张四列表，包含首轮 `（无）` 以及三个完整专家名称，不包含 JSON、长期职责或额外章节；
4. 三个专家长期提示词包含专业差异、工作区执行原则、专家 JSON 和流程控制，并禁止跨专家调度；
5. 三个普通 Skill 均只有 `执行规则` 和 `结束条件`，且不含平台协议字段；
6. 所有 JSON、YAML Frontmatter 和脚本 manifest 均可解析；
7. 定向运行协作资源、主持人和专家执行相关测试，并执行格式检查。

## 成功标准

- 提示词装配后，每一层只承担现行合同规定的职责；
- 主持人首轮和后续阶段都能在四列表中找到可判断分支；
- 专家非空长期提示词不会丢失平台默认输出合同；
- 现有三类业务能力、工具绑定和确认门禁保持不变；
- 测试不再把主持人 JSON 错误地要求在主持人 Skill 中，也不再把完整专家协议错误地排除在专家长期提示词之外。
