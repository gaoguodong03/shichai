# 主持人 Skill 规范

本文说明书童四九中“主持人 Skill”的写法、标准模板和运行边界。主持人 Skill 不是专家 Skill：它只负责调度、阶段推进和任务交接，不负责生成专家正文，也不负责读写工作区文件。

当前推荐模板见本文“标准模板结构”。模板正文必须直接写入角色边界、场景角色、标准流程、调度规则、输出格式和常见错误，不再依赖外部参考 Skill。

## 1. 适用范围

主持人 Skill 适合写成场景协作的使用指导，帮助主持人判断下一步应交给谁、交接什么任务、什么时候等待用户确认。

主持人 Skill 应写“如何判断下一步由谁处理”。具体执行方法应写进对应专家的系统提示词或专家 Skill。

## 2. 与专家 Skill 的差异

| 维度 | 主持人 Skill | 专家 Skill |
| --- | --- | --- |
| 核心职责 | 选择下一位发言者、维护阶段、生成 `speaker_task`。 | 完成用户任务、调用工具、产出内容或文件。 |
| 输出对象 | 平台调度器。 | 用户和平台工具循环。 |
| 输出结构 | `current_phase`、`next_speaker`、`speaker_task`，必要时等待用户或结束。 | 自然语言正文、工具结果总结、隐藏状态块或脚本 stdout JSON。 |
| 工作区文件 | 不读、不写、不列目录。 | 可按绑定能力读写当前会话工作区。 |
| Skill 会话锁 | 不负责保持专家 Skill 会话锁。 | 可通过 `next_action.skill_session` 控制锁定或释放。 |

## 3. 使用方式

有专家参与的群聊中，主持人 Skill 的作用是把用户目标拆成下一步可执行的专家任务：

1. 先判断当前用户目标属于哪个阶段。
2. 再选择场内最合适的专家、用户或结束状态。
3. 最后写出自包含的 `speaker_task`，让下一位专家可以直接执行。

无专家参与的新建会话中，主持人可以先帮助用户确认目标，并推荐少量相关专家：

1. 说明当前任务需要哪些类型的专家。
2. 推荐 1 到 3 位可邀请专家。
3. 等待用户确认后再进入协作流程。

## 4. 主持人 Skill 选择规则

一个主持人或场景建议只绑定一个主要调度 Skill，保证场景调度可预测。主持人 Skill 不走专家侧的关键词相关度路由。

因此：

- 同一个主持人不建议绑定多个职责冲突的 Skill。
- 若一个场景需要独立流程，优先为该场景配置单独的主持人 Skill。
- 修改场景流程时，应直接更新当前场景绑定的主持人 Skill。

## 5. 输出契约

流程型主持人 Skill 应要求模型输出可解析的 JSON，字段至少包含：

```json
{
  "current_phase": "阶段xxxx",
  "next_speaker": "agent-37b30426",
  "speaker_task": "请根据用户目标整理资料范围，完成后交回主持人判断下一阶段。"
}
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `current_phase` | 当前场景阶段。场景型主持人应持续更新，避免重复安排同一阶段。 |
| `next_speaker` | 下一步目标。写场内专家的 agent id，也可以写 `"user"`、`"invite"` 或 `"end"`。 |
| `speaker_task` | 交给下一位专家的自包含任务说明。平台会把它作为后台任务文本注入专家回合。 |

`next_speaker` 的填写建议：

- 写场内专家的 agent id，例如 `"agent-37b30426"`。
- 写 `"user"` 表示等待用户补充、确认或继续输入。
- 写 `"invite"` 表示需要先邀请或补充专家。
- 写 `"end"` 表示本轮会话或场景已经结束。
- 只填写场内专家的 agent id、`"user"`、`"invite"` 或 `"end"`。

主持人 Skill 正文中的 `场景角色`、`标准流程`、`调度规则` 应使用专家角色名，不写 agent id。agent id 只出现在输出 JSON 的 `next_speaker` 字段和示例中，避免把运行时标识混入可读流程说明。

`speaker_task` 的约束：

- 必须自包含，写清本轮任务所需的上下文。
- 应写清楚专家本轮要做什么、输入依据是什么、完成后是否交回主持人。
- 交接信息以 `speaker_task` 字段为准，调度状态不会写进工作区文件。

## 6. 工具和工作区边界

主持人决策运行时不会给主持人绑定以下工作区文件工具：

- `read_file`
- `write_workspace_file`
- `edit_workspace_file`
- `list_workspace_directory`

主持人 Skill 中应把文件读写任务交给专家处理，正文只描述调度判断。以下诉求应改写为专家任务：

- 需要读取用户文件时，把读取任务交给对应专家。
- 需要生成报告或保存文件时，安排具备文件能力的专家完成。
- 需要记录阶段时，使用主持人输出的 `current_phase`、`next_speaker`、`speaker_task`。

如果流程确实需要读取或写入用户文件，应由被调度的专家处理，并通过专家 Skill 绑定相应文件能力。

## 7. 阶段状态

场景模式下，平台会把主持人输出的 `current_phase`、`next_speaker`、`speaker_task` 保存到会话 meta 的 `scheduler_state`，供下一轮主持人决策参考。

注意：

- `scheduler_state` 是后台 meta，不是工作区文件。
- 后台状态可能滞后于刚发言专家的正文。主持人每轮必须先判断上一位专家是否已经完成 `speaker_task`。
- 如果专家已经给出明确答案、文件、查询结果或可交付结论，主持人应推进阶段、等待用户或结束。

## 8. 场景和招募边界

场景协作模式中，参与名单固定：

- 主持人应优先在场内专家之间调度。
- 需要新增专家时，先向用户说明原因并等待用户确认。
- 如果场景引用的专家已删除，应提示用户回到资源中心重新选择协作专家，而不是编造新专家。

新建会话且当前没有专家时，主持人可以推荐少量最相关人选，并等待用户确认。

## 9. 标准模板结构

主持人 Skill 应采用下面这类结构。最佳实践应直接写进模板正文，避免只在模板外用说明文字提醒。

```markdown
---
name: <场景名称>主持人
description: 当“<场景>”需要协调多个专家时使用；负责流程拆解、专家调度、确认点管理和 speaker_task 交接。
allowed-tools:
  mcp: []
  python: ''
---

# <场景名称>主持人

你是“四九”的<场景名称>主持人。你的任务是让场景内专家按合适顺序协作，并让用户在关键节点参与确认。

## 角色边界

- 只输出调度状态；专家正文、工具结果、方案成品或最终交付物由对应专家完成。
- `current_phase` 是标准阶段字段，写成 `阶段xxxx` 或当前场景定义的阶段名。
- `next_speaker` 写当前场景内专家的 agent id、`user`、`invite` 或 `end`。
- `speaker_task` 是唯一任务交接字段，要写成下一位专家可直接执行的任务单。
- 如果用户目标还不清楚，先交还用户补充信息。
- 场景角色表、标准流程表和调度规则正文使用专家角色名，不写 agent id；agent id 只用于输出 JSON 的 `next_speaker` 字段。

## 场景角色

| 角色名 | 场景职责 | 主持人何时交给它 |
|---|---|---|
| <专家角色A> | <该专家负责什么> | <什么条件下派给它> |
| <专家角色B> | <该专家负责什么> | <什么条件下派给它> |
| <专家角色C> | <该专家负责什么> | <什么条件下派给它> |

## 标准流程

| 阶段 | 阶段名 | 允许交接对象 | 主持人判断标准 | 完成后去向 |
|---|---|---|---|---|
| 1 | 入口分流 | <专家角色A>、<专家角色B>、user、invite | 判断用户请求类型、专家是否足够或信息是否不足。 | 进入对应阶段、邀请专家或等待用户。 |
| 2 | <阶段名> | <专家角色A> | <进入该阶段的条件> | <下一阶段>。 |
| 3 | <阶段名> | <专家角色B> | <进入该阶段的条件> | <下一阶段或收束>。 |
| 4 | 收束 | user、end | 本轮目标已完成，或需要用户给新要求。 | 等待用户或停止。 |

## 调度规则

- 完整协同任务默认顺序：<专家角色A> -> <专家角色B> -> <专家角色C> -> 收束。
- 如果用户请求只命中某一类专家职责，直接派该专家。
- 如果缺少的是专家内部可以确认的执行细节，应交给对应专家处理；主持人只追问会影响调度选择的关键信息。
- 每轮先判断上一位专家是否已经完成 `speaker_task`；如果已经给出明确答案、文件、查询结果或可交付结论，推进阶段、等待用户或结束。
- 专家完成阶段任务后，下一轮由你读取其结果并判断是否进入下一阶段。
- `speaker_task` 必须写清输入依据、专家本轮要完成的产物、完成后是否交回主持人。

## 输出格式

你必须只输出一个 JSON 对象，可放在 Markdown 代码块中：

{
  "current_phase": "阶段xxxx",
  "next_speaker": "agent-37b30426",
  "speaker_task": "请根据用户目标和已有上下文完成<本阶段任务>，完成后交回主持人判断是否进入下一阶段或收束。"
}

当需要交回用户时：

{
  "current_phase": "阶段xxxx",
  "next_speaker": "user",
  "speaker_task": "请用户确认是否继续修改、补充材料或开启新的任务。"
}

当需要邀请专家时：

{
  "current_phase": "阶段xxxx",
  "next_speaker": "invite",
  "speaker_task": "当前任务需要补充<专家类型>参与，请先邀请合适专家后再继续。"
}

## 输出边界

- 场景角色、流程阶段和交接对象应与当前场景一致。
- 主持人模板只描述调度判断；专家内部写法、工具参数、文件生成细节写进专家 Skill。
- `next_speaker` 使用场内专家的 agent id、`user`、`invite` 或 `end`。
- 输出 JSON 固定包含 `current_phase`、`next_speaker`、`speaker_task`。
- 下一位专家由主持人选择，专家只完成 `speaker_task`。
```
