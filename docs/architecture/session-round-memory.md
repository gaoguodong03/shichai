# 会话、轮对话与记忆设计

本文档明确「轮对话」「会话」「记忆」的层级概念，以及如何将合适的上下文交给大模型。

---

## 一、层级概念

### 1.1 轮对话（Round / Session）

**轮对话** = 一次独立对话会话的完整生命周期。

- **新建对话**：创建新的轮对话
- **历史会话**：之前保存的轮对话
- **当前对话**：用户正在进行的轮对话

术语上，`session_id` 即标识一轮对话。新建对话、历史会话列表、切换会话，都在这一层操作。

```
┌─────────────────────────────────────────────────────────────┐
│  轮对话层（Session / Round）                                    │
│  - 新建对话、历史会话、当前对话 都在这一层                         │
│  - 每轮有唯一 session_id                                       │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ 包含
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  轮内对话（Turn）                                              │
│  - 用户消息 + 助手回复 = 一次「对话」                             │
│  - 本轮的每一次交互都在这里                                       │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 轮内对话（Turn）

**轮内对话** = 一轮中的一次完整交互。

- 用户输入一条消息
- 助手进行一次回复（可能包含多轮工具调用，但对用户体现为一次回复）
- 上述「用户消息 + 助手回复」合称为一次 **Turn**

多轮对话即：同一 session 内，多次 Turn 依次进行。

## 二、数据模型

### 2.1 当前实现（简化）

```
Session (session_id)
  └── messages: [HumanMessage, AIMessage, HumanMessage, AIMessage, ...]
      每对 (HumanMessage, AIMessage) 即一次 Turn
```

### 2.2 建议的语义划分

| 概念       | 实现对应            | 说明                         |
|------------|---------------------|------------------------------|
| 轮对话     | `session_id`        | 新建对话、历史会话的粒度      |
| 轮内对话   | 一对 (user, assistant) | 一次 Turn                   |
| 当前 Turn  | 本次请求 + 即将生成的回复 | 还在进行中                 |

## 三、记忆设计：给大模型什么

### 3.1 核心原则

> **传给大模型的，应是「本轮中每一次对话的摘要或需要的内容」，而不是直接塞入完整原始历史。**

原因：

1. **上下文窗口有限**：完整历史易超出 token 限制
2. **信息密度**：摘要能保留关键信息，减少噪音
3. **长期连贯**：多轮后仍能保持对前面讨论的把握

### 3.2 记忆内容设计

对每一轮对话（Session）中的**每一次 Turn**，可维护：

| 字段         | 说明                                   |
|--------------|----------------------------------------|
| 原始消息     | 用户消息 + 助手回复的完整内容（持久化用） |
| 摘要         | 该 Turn 的简短摘要（供后续 LLM 上下文）  |
| 关键信息     | 可选：结构化提取（如用户偏好、重要结论） |

**传给 LLM 的上下文** = 各 Turn 的「摘要」或「关键信息」拼接，而不是原始全文。

### 3.3 摘要生成策略

1. **及时生成**：每次 Turn 结束后，用 LLM 对「用户消息 + 助手回复」生成简短摘要
2. **截断备选**：若暂不接入 LLM 摘要，可用规则截断（如每条消息前 N 字），作为过渡方案
3. **滑动窗口**：保留最近 K 个 Turn 的摘要，更早的 Turn 可合并或丢弃

### 3.4 与现有实现的对应

| 现有实现              | 说明 |
|-----------------------|------|
| `_CHAT_HISTORY[sid]`  | 继续存完整消息，用于持久化、导出、前端展示 |
| `_TURN_SUMMARIES[sid]` | 每轮摘要，**只保留最近 10 轮**（`_HISTORY_WINDOW_TURNS=10`） |
| `_build_history_summary()` | 优先用 Turn 摘要，只取最近 10 轮；无摘要时从历史取最近 10 轮做预览 |
| `history_summary`     | 作为「最近 10 轮 Turn 摘要」传给技能选择和执行 |

## 四、流程示意

```
用户发起新消息（当前 session）
         │
         ▼
┌─────────────────────────────────────┐
│ 1. 加载本轮历史消息                   │
│    _CHAT_HISTORY[session_id]         │
└─────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────┐
│ 2. 构建「本轮记忆」                    │
│    - 每个 Turn → 摘要或关键内容        │
│    - 拼接成 history_summary           │
└─────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────┐
│ 3. 技能选择                          │
│    输入：用户消息 + history_summary   │
└─────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────┐
│ 4. 技能执行                          │
│    输入：用户消息 + history_summary   │
│    （均基于 Turn 摘要，非原始全文）    │
└─────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────┐
│ 5. 保存本轮新 Turn                   │
│    - 完整消息追加到 _CHAT_HISTORY    │
│    - （可选）生成该 Turn 摘要并缓存   │
└─────────────────────────────────────┘
```

## 五、实现建议

### 5.1 短期（保持现状可接受时）

- 明确文档中的「轮 vs Turn」概念
- 继续使用 `_build_history_summary()` 的截断逻辑，但按 Turn 为单位组织（每对 user+assistant 为一个单元）

### 5.2 中期（引入摘要）

1. 新增 `TurnSummary` 结构：`{turn_index, user_summary, assistant_summary}` 或合并为 `turn_summary`
2. 每次 Turn 结束后，异步调用 LLM 生成摘要并缓存（如 `_TURN_SUMMARIES[session_id]`）
3. `_build_history_summary()` 改为拼接这些摘要，而非原始消息截断

### 5.3 长期（可选）

- 关键信息抽取（实体、偏好、结论）
- 跨 Session 的长期记忆（若产品需要）
