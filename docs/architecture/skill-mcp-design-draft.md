# Skill + MCP 设计（已实现）

本文档描述「先选技能、再执行技能」的两阶段设计，已按此实现。

---

## 核心流程

每一轮 chat 的流程：

```
用户输入
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 第一次调用大模型（技能选择）                                │
│ 输入：用户输入 + 各 skill 的 name（+ description，若有）     │
│ 输出：选中的 skill 名称                                    │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 第二次调用大模型（技能执行）                                │
│ 输入：选中 skill 的完整内容 + 用户问题                      │
│ 行为：按 skill 步骤执行，某一步需要时调用 MCP 工具           │
│ 输出：工具执行结果 / 大模型答复                             │
└─────────────────────────────────────────────────────────┘
```

---

## 要点

### 1. 第一次调用大模型

- **只给**：用户输入 + 每个 skill 的 `name`（若有 `description` 则也给出）
- **不给**：skill 的完整内容（避免 token 过多）
- **目的**：让大模型返回「本次应使用哪个 skill」

### 2. 第二次调用大模型

- **给**：选中的 skill 的完整内容 + 用户问题
- **行为**：按 skill 中的 step 执行；某一步需要外部能力时，调用 MCP 工具（通过 Python MCP SDK）
- **输出**：工具执行结果或大模型最终答复

### 3. 多轮 chat（第二轮及以后）

- 在输入中**加入**：之前轮次的**历史会话摘要**
- 摘要需包含：本轮需要哪些上下文（如之前选中的 skill、关键结论等）

### 4. 按技能过滤工具（chat.py）

**问题**：选中某技能后，若仍传入所有 MCP 工具，会导致：
- 工具列表过长，模型处理变慢
- 历史摘要中其他技能的对话干扰当前任务

**改动**：选中某技能后，只传入该技能对应的 MCP 工具：

| 技能 | 传入的 MCP Server |
|------|-------------------|
| amap-maps | amap-maps |
| app-icon-generator | volces-icon |
| wechat-article-writer | linkup、exa、fetch、mem0 |

映射关系在 `chat.py` 的 `_MCP_SERVER_TO_SKILL` 中维护；反向推导得到「技能 → MCP server_ids」。

**回退**：若该技能关联的 MCP 无可用工具（例如 amap-maps MCP 未启动），则回退为传入全部工具，并打 warning 日志。

---

## 与当前实现的差异

| 维度 | 当前实现 | 本设计 |
|------|----------|--------|
| 调用次数 | 一个 ReAct 循环，多次调用 | 每轮固定 2 次：选技能 → 执行技能 |
| 技能内容 | 所有 skill 的 name+description 一次性注入 | 第一次只给 name+description；第二次只给选中 skill 的完整内容 |
| 历史 | 原始消息历史（最多 N 条） | 历史会话摘要 + 必要上下文 |
