新建会话模式
1）用户发出请求
2）四九根据用户请求，以及系统默认的提示词（和Skill）完成专家的推荐
3）用户选择邀请或是不邀请专家加入群聊
4）用户发出请求
5）如果用户未邀请任何专家加入群聊，则转向“2）
6）如果用户已邀请专家加入群聊，则四九根据用户请求，以及系统默认的提示词（和Skill）选择专家（）处理此请求
7）专家根据用户请求，以及专家提示词和配置的Skill，选择Skill（a）处理此请求
8）用户发出请求，专家继续使用Skill（a）处理此请求，直至Skill（a）运行完毕或是用户主动退出Skill（a）。注意：此过程中四九并不会处理用户请求。
9）转向“6）”，直至四九根据上下文，以及场景提示词（和Skill）认为本场景结束


场景模式
1）用户发出请求
2）四九根据用户请求，以及场景中四九的提示词（和Skill）选择专家
3）专家根据用户请求，以及专家提示词和配置的Skill，选择Skill（a）处理此请求
4）用户发出请求，专家继续使用Skill（a）处理此请求，直至Skill（a）运行完毕或是用户主动退出Skill（a）。注意：此过程中四九并不会处理用户请求。
5）转向“2）”，直至四九根据上下文，以及场景提示词（和Skill）认为本场景结束


当前实现补充（在上述规则后追加）
一、路由优先级（从高到低）
1）用户消息以 @专家 开头时，强制由该专家处理（覆盖常规调度）。
2）用户文本显式点名场内专家（如“问问研讨教师……”）时，优先直达该专家处理，并清理旧的 skill 锁，避免误续跑到上一位专家。
3）若存在有效 Skill 会话锁（skill_session_owner_name 且该专家仍在群内），则跳过四九，直接续跑该专家；用户明确说“交给主持人 / 换专家 / 结束当前技能”等时，会先清理 Skill 锁再回到四九调度。
4）否则进入四九调度，由四九根据上下文选择 next_speaker。

二、专家执行与 Skill 会话
1）专家被选中后，在同一轮内直接执行，不再只“点名后等待下一条用户消息”。
2）专家执行完成后，若无自动继续信号，返回等待用户输入（AWAITING_USER）。
3）当用户明确表达“结束 skill/退出 skill/交给主持人”等语义时，清理 skill 锁并回到四九调度链路。
4）Skill 会话由脚本或 MCP 工具 stdout JSON、或专家隐藏状态块中的 `next_action` 判定；字段含义与组合见 [skill-session-flow.md](../skills/skill-session-flow.md)，与主持人/入口路由的合成状态机见 [group-orchestration-fsm.md](./group-orchestration-fsm.md)。

三、主持人可见消息规则（平台固定话术）

主持人只负责调度，不向用户复述需求或代答。平台根据 `next_speaker` 生成固定话术，完整状态机见 [group-orchestration-fsm.md](./group-orchestration-fsm.md)。

| next_speaker | 用户可见 |
| --- | --- |
| 场内 `agent-xxx` | `下面由 {专家名} 发言。` |
| `invite`（含 0 专家需组队） | 固定「我推荐以下专家加入讨论：…」 |
| `end` | `任务结束，请打开新对话。`（吸收态） |
| `user` | **无主持气泡**；用户说完后重新走主持人调度 |

注意：`next_speaker=user` 与 `next_action.skill_session=keep` 不同。后者是专家声明的 Skill 锁，下条用户消息直达专家，主持人全程 bypass（见上文「一、路由优先级」第 3 条及 [group-orchestration-fsm.md](./group-orchestration-fsm.md) L2）。

四、结束与中断
1）`next_speaker=end`：会话进入 COMPLETED；持久化后进入吸收态，后续输入仍返回结束话术（见 [group-orchestration-fsm.md](./group-orchestration-fsm.md)）。
2）需要用户补充信息、上下文不足、工具异常、轮次预算到达上限等情况：进入等待用户状态，并通过中断原因提示用户下一步。

五、前端提示条行为（与后端编排对应）
1）“四九已帮您切换专家：X”用于提示路由切换。
2）当本轮实际出现专家 assistant 消息并收到 end 事件后，自动关闭该提示条。
3）仅主持人点名或主持人收尾而未产生专家消息时，不自动关闭该提示条。
