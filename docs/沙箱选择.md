请把 OpenSandbox 作为底层沙箱基础设施来设计实现。
OpenSandbox 已经是开源项目，可直接使用，它提供统一的 sandbox API、生命周期管理、命令执行、文件操作、卷挂载，以及 Docker/Kubernetes 运行时能力。请基于这个前提设计我的系统适配层，而不是重新实现一套底层 runtime。

我的目标是：

在我的智能体平台中封装一层 OpenSandboxAdapter / SandboxService
由平台负责“用户 / 会话 / skill / 工作区 / 权限映射”
由 OpenSandbox 负责“沙箱创建、隔离执行、文件系统操作、命令执行、资源限制、生命周期管理”
代码结构上要为未来迁移到 Kubernetes、gVisor、Kata、Firecracker 预留扩展点，因为 OpenSandbox 官方已经支持 Docker/Kubernetes runtime，并提供 secure container runtime 配置思路。


这次要采用的架构原则
1. 底层直接用 OpenSandbox

请不要重新发明一套底层沙箱 runtime。
请直接把 OpenSandbox 当成底层执行基础设施，在我的系统中实现一层适配器。

适配层负责：

用户 / 会话 / skill 的业务建模
会话与沙箱实例的映射
工作区目录与 volume mount 的映射
skill 脚本目录与只读挂载的映射
依赖镜像或基础环境的复用策略
执行请求与结果的封装
平台侧权限控制与审计日志

OpenSandbox 开源且 Apache 2.0 许可证，可直接使用，它提供统一的 sandbox API、生命周期管理、命令执行、文件操作、卷挂载，以及 Docker/Kubernetes 运行时能力。
和我们讨论的有出入的是：沙箱的执行粒度仍然是按照会话建立而不是按照用户建立，沙箱的依赖是按照skill依赖哈希复用而不是按照用户或者会话重复下载。

1. 执行隔离按会话做
每个会话对应一个独立 sandbox 实例，每个 sandbox 只能访问当前会话对应的 workspace
同一用户的不同会话不共享同一个可执行文件系统视图

2. 依赖复用按 skill 依赖集合做
不要让每个会话都重新安装 Python 包，而是基于 requirements.txt / pyproject.toml / lockfile 计算依赖哈希
相同依赖集合应复用同一个基础镜像或基础环境，会话沙箱应从“已准备好的依赖镜像模板”启动，而不是运行时临时装包。

3. 目录挂载策略
按 OpenSandbox 支持的 volume mount 思路设计（这点和我们出入不大）：
当前 session workspace 挂载到沙箱内 /workspace，可读写
当前 skill 的 scripts 挂载到 /skill/scripts，只读
执行时在沙箱内运行 /skill/scripts/...
输入输出文件统一在 /workspace
